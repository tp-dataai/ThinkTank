## 1. 5 万/月岗位在看什么

5 万/月的岗位通常不是“会调 API”就能拿到，面试官会从六个维度交叉验证：

| 维度 | 面试官想确认 | 你的项目证据 |
|---|---|---|
| RAG 全链路 | 你是否理解导入、切分、向量、检索、重排、生成每一环的取舍 | 基础链路完整，能讲 chunk 300/50、混合检索、RRF、断崖式 top-k |
| 系统设计 | 能否从需求推到架构，而不是堆框架 | 统一 Markdown 归一化、GraphRAG + RRF、Agentic 状态机、引用溯源 |
| 评估能力 | 能否定义指标、构造黄金集、做消融 | 第 5/6/7/8 节的评估方案，第 10.2 节完整评估体系 |
| 工程化 | 幂等、降级、超时、重试、可观测、安全 | file_title_id 幂等、MCP 软降级、有界重试、上传校验、引用元数据 |
| 成本与延迟 | 是否知道每次调用花在哪、怎么省 | 最坏 13 次额外 LLM 调用、路由前置、top-k 控制、缓存思路 |
| 技术判断力 | 能否说“不”，能否解释为什么不用某个热门方案 | 不做 CLIP、不做微软 GraphRAG 社区摘要、不做自由 Agent、不让模型写页码 |

### 1.1 你的差异化亮点（面试反复用）

1. **统一归一化**：图片、音频、视频全部转 Markdown，复用同一条切分/向量/检索链路，而不是为每种模态造一套系统。
2. **局部 GraphRAG + RRF**：不追求大而全的图，按 `item_name` 锚定关系子图，图证据和向量证据统一融合。
3. **有界 Agentic**：路由 + 证据评估 + 最多 2 次重试 + 本地不足自动升级网络，但不引入自由 Agent，保留 SSE 可观测性和成本上限。
4. **可验证引用**：页/段元数据随 chunk 入库，模型只输出 `[n]`，后端映射文档/页/链接，PDF 可一键跳转。
5. **工程纪律**：幂等、软降级、参数化查询、上传白名单/大小限制/路径穿越防护、验收矩阵。

### 1.2 不同轮次的重点

| 轮次 | 面试官重点 | 你优先准备 |
|---|---|---|
| 一面/基础面 | 八股、代码、项目是否真的做过 | 第 2.4 节 30 秒介绍、第 11 节八股、第 14 节白板 |
| 二面/项目深挖 | 取舍、失败模式、指标、你是否主导 | 第 5/6/7/8 节各 3 分钟讲解 + 每节 10 问 |
| 三面/系统设计 | 规模、成本、权限、可观测、演进 | 第 10 节全部、第 9 节协同 |
| 交叉面/负责人 | 技术判断力、边界、沟通 | 第 9.4 节缺陷、第 13 节压力面 |
| HR 面 | 动机、协作、稳定性 | 第 12 节 STAR、第 13.3 反问 |

### 2.2 架构总览

```text
【导入链路】
文件(PDF/MD/图片/音频/视频)
   ↓
NodeEntry：校验 + file_type 路由
   ↓
转换器：PDF→MinerU→MD；图片→image+MD；音频→ASR→MD；视频→抽音轨+关键帧→MD
   ↓
NodeMDImg：VL 摘要 + MinIO 上传 + Markdown alt/URL 替换
   ↓
NodeDocumentSplit：标题粗切 + RecursiveCharacterTextSplitter 细切（300/50）
   ↓
NodeItemNameRecognition：LLM 主体识别 + Milvus 主体名表
   ↓
NodeCitationEnrich：PDF 页/块定位 → source_meta（文档/页/段/URL）
   ↓
NodeBGEEmbedding：BGE-M3 稠密 + 稀疏向量
   ↓
NodeImportMilvus：file_title_id 幂等写入
   ↓
（可选）NodeGraphExtraction：LLM 抽实体/关系 → Neo4j

【查询链路】
用户问题
   ↓
NodeItemNameConfirm：历史 + LLM 提取主体/改写 + 主体名混合检索/对齐
   ↓
NodeQueryRouter：kb / web / both / direct
   ↓
[普通向量检索 | HyDE 检索 | 图检索 | Web 搜索]（按路由选择）
   ↓
RRF 融合
   ↓
Rerank（Qwen rerank + 断崖式动态 top-k）
   ↓
NodeRelevanceJudge：证据是否足够
   ├─ 足够 / 达到重试上限
   │     ↓
   │  AnswerOutput：context 带 [n] → 模型只输出 [n] → 后端映射 sources
   │     ↓
   │  chat.html：行内引用 + 参考来源 → PDF #page=N
   └─ 不足 → 重写/升级 → 有界重试
```

## 4. 架构总览与关键取舍

### 4.1 关键设计决策表（面试高频）

| 决策 | 选择 | 理由 | 代价 / 何时改 |
|---|---|---|---|
| 多模态表示 | 统一转 Markdown 文本 | 复用现有切分/向量/检索/重排；BGE-M3 是文本模型；可解释 | 丢失视觉相似性；需要“以图搜图”时加 CLIP/BGE-VL 独立 collection |
| 文档切分 | 标题粗切 + 300/50 细切 | 保留章节语义；代码围栏不误切；表格不拆 | 长表格/超长章节可能不理想；可加语义切分 |
| 检索 | 稠密 + 稀疏混合 | 语义 + 关键词互补；中文专有名词/型号更稳 | 两次检索 + 融合；Milvus 资源 |
| 融合 | RRF | 不同来源量纲不同，只看排名；实现简单稳定 | 丢弃原始分数；可加权重/学习融合 |
| 重排 | Qwen rerank + 断崖检测 | 统一语义打分；动态 top-k 控制噪声 | 额外延迟/成本；阈值需按数据调 |
| 主体锚定 | item_name 过滤 | 缩小检索范围、避免跨主题串味 | 依赖主体识别质量；无匹配时需 web 回退 |
| 图检索 | 局部实体关系子图 | 多跳/关系/可解释；成本可控 | 不是全局主题摘要；需要实体质量 |
| Agentic | 路由 + 评估 + 有界重试 | 自适应、可观测、成本上限 | 多几次 LLM 调用；路由/评估可能误判 |
| 引用溯源 | 元数据驱动，模型只出 `[n]` | 页码/链接可校验，不会编造 | 增加页映射和 Milvus 字段；扫描件/跨页有边界 |
| 自由 Agent | 不做 | SSE 进度、成本、安全、可复现 | 开放式工具调用场景另建服务 |

### 4.2 一致性与幂等

- **Milvus**：`file_title_id = md5(file_title)`；导入前按 `file_title_id` 删除旧切片，再插入。
- **Neo4j**：同一事务内删除该文件的旧关系 → MERGE 实体 → MERGE 关系 → 清理孤立实体。
- **MinIO**：图片按 `{MINIO_IMG_DIR}/{日期}/{stem}` 先清后传；媒体按 `media/{日期}/{stem}` 覆盖。
- **引用元数据**：`source_meta` 随 chunk 一起重写；页映射文件随导入重新生成；重复导入不累积旧引用。
- **Mongo**：会话历史按 session 查询，不参与检索一致性；`sources` 历史回放是二期。
- **注意**：跨日期重复导入会留下旧日期目录；生产需要清理策略/版本号。

### 4.3 故障降级原则

| 场景 | 导入侧 | 查询侧 |
|---|---|---|
| Neo4j 不可用 | 任务失败（不能静默丢图） | 图检索返回空，继续向量/Web |
| MCP 不可用 | 不涉及 | Web 返回空，评估后回答或提示不足 |
| ASR/ffmpeg 失败 | 明确失败 | 不涉及 |
| 评估/路由 JSON 失败 | 不涉及 | 路由兜底；评估按“有结果即足够” |
| 页映射/引用元数据失败 | 降级为文档级引用，不阻断导入 | 不涉及 |
| 引用编号非法/模型不引用 | 不涉及 | 过滤非法编号；无引用时兜底展示前 3 个来源 |
| 文档 URL 不可访问 | 不涉及 | 仍展示来源文字；生产用签名 URL/网关 |
| 向量库不可用 | 任务失败 | 查询失败（核心路径） |

## 5. 多模态数据处理

### 5.1 业务问题

知识库不只有 PDF/Markdown，还有图片、音频、视频。如果每种模态单独建索引、单独写检索逻辑，系统会迅速碎片化。目标是用最小改动让多模态内容进入现有 RAG 链路。

### 5.2 架构与数据流

```text
NodeEntry（file_type 路由）
  ├─ pdf   → NodePDFToMD（MinerU）─┐
  ├─ md    → （直接）              │
  ├─ 图片  → NodeImageToMD ────────┤
  ├─ 音频  → NodeAudioToMD（ASR）──┤
  └─ 视频  → NodeVideoToMD（抽帧）─┘
                                   ↓
                              NodeMDImg
                     （VL 摘要 + MinIO + alt 替换）
                                   ↓
                          NodeDocumentSplit
                                   ↓
                         后续链路完全复用
```

### 5.3 3 分钟讲解稿

> “多模态这块我没有为每种模态建一套向量库，而是做了一个统一约定：所有模态先转成 Markdown。图片直传时，我在 `{stem}/images/` 下放一份统一命名的图片，写一个只包含图片引用的 Markdown，然后完全复用原来的 `NodeMDImg`——它会调 VL 模型生成 50 字摘要、上传 MinIO、把 Markdown 的 alt 和 URL 替换掉。音频用本地 FunASR 转成 16k 单声道，输出带标题的 Markdown；视频用 ffmpeg 抽 16k 音轨做 ASR，每 30 秒抽一帧放到 images 目录，拼成 Markdown，关键帧继续复用 `NodeMDImg` 的摘要逻辑。这样切分、主体识别、BGE-M3、Milvus、RRF、Rerank 全部不用改。媒体 URL 我放在每个 chunk 的 content 前缀里，查询侧从检索结果提取 `media_urls` 回传前端。入口用 `file_type` 路由替代原来的 PDF/MD 布尔开关；上传接口加了后缀白名单、200MB 上限、basename 防路径穿越。取舍是放弃了视觉相似检索，换来链路复用和成本可控；如果以后要做以图搜图，我再加一个 CLIP/BGE-VL 的独立 collection。”

### 5.4 代码级细节（面试官可能追问）

| 点 | 实现 |
|---|---|
| file_type 路由 | `pdf/md/image/audio/video`，集中在一张后缀映射表，入口只校验和路由 |
| 图片直传 | `NodeImageToMD` 统一命名为 `image.{ext}`，避免中文/括号破坏 Markdown 图片正则 |
| 图片增强 | 复用 `NodeMDImg`：上下文前后各 100 字 + VL 摘要 ≤50 字 + MinIO URL + alt 替换 |
| 限流 | 令牌桶 `deque(maxlen=30)`，30 RPM，避免 VL API 限流 |
| 音频 | FunASR `paraformer-zh + fsmn-vad + ct-punc`；统一 16k 单声道 wav |
| 视频 | ffmpeg `fps=1/30` 抽帧；时长上限 1800 秒；抽音轨 ASR；单帧摘要复用 VL |
| 媒体 URL | 写入 chunk content 前缀；`NodeAnswerOutput` 正则提取 `media_urls` 给前端 |
| 修复 | `NodeMDImg` 的 upload_dir 多余空格、URL 编码、图片 MIME 类型、无图片早退 |

### 5.5 关键取舍

| 问题 | 选择 | 为什么不选另一个 |
|---|---|---|
| 图片怎么检索 | VL 摘要转文本 | CLIP 只能做相似度，不能直接回答文本问题；多一套模型和索引 |
| 音频怎么处理 | 本地 FunASR | 云端 ASR 读不到内网 MinIO；本地数据不出内网、成本可控 |
| 视频怎么理解 | ASR + 关键帧 | 视频大模型成本高、时序定位难；当前场景讲解/演示为主 |
| 媒体字段 | 放 content，不改 Milvus schema | 避免重建 collection；代价是按模态过滤不方便 |
| 图片文件名 | 统一 `image.{ext}` | 原文件名可能含中文/空格/括号，破坏 Markdown 正则和 URL |

### 5.6 难点与解决（STAR 素材）

1. **VL API 限流**：30 RPM 令牌桶；失败/空摘要要有兜底；长视频帧多时耗时明显，抽帧间隔可调。
2. **图片 MIME 错误**：原代码固定 `image/jpeg`，直传 PNG 会类型不匹配；改为 `mimetypes.guess_type`。
3. **MinIO URL 空格**：`upload_dir` 里有多余空格；改为无空格 + `urllib.parse.quote`。
4. **无图片文档白跑**：音频/纯文本没有 images 目录，原逻辑仍走 MinIO 列表/删除；加早退。
5. **路径穿越**：上传文件名只取 basename；后缀白名单；大小上限。

### 5.7 怎么评估多模态效果

| 指标 | 方法 |
|---|---|
| 导入成功率 | 各类型上传任务 completed / 总数 |
| ASR WER | 30~60 分钟人工标注音频，`(S+D+I)/N` |
| 关键帧覆盖率 | 视频时长 / 抽帧数；人工看关键画面是否覆盖 |
| 图片检索命中 | 构造图片内容问题，看 Recall@k 和答案是否引用正确图片 |
| 答案引用率 | 回答中是否带回正确的图片/媒体 URL |
| 端到端通过率 | 100 题人工 rubric：正确、部分正确、错误、拒答 |

### 5.8 高频追问（10 问）

**Q1：为什么不做真正的多模态向量检索？**
> 当前问题是“根据内容找片段”，文本足够表达；BGE-M3 是文本模型，统一转文本能复用整条链路。CLIP 适合图-图/文-图相似，不适合直接回答文本问题，而且要多一套模型、索引、融合和评估。只有“以图搜相似图”成为核心需求时才值得加。

**Q2：50 字摘要会不会丢关键信息？**
> 会，所以摘要提示词带了前后各 100 字上下文，并要求保留型号、接口、步骤等关键信息；原图 URL 保留，答案可以回链。对结构图/接线图，MinerU 的 OCR/图注也会补充。高价值场景可以加 OCR 或结构化抽取，并用图片问答集评估摘要召回。

**Q3：为什么音频用本地 ASR？**
> 云端 ASR 需要一个公网可访问的音频 URL，我的 MinIO 在内网；本地 FunASR 数据不出内网、中文效果好、GPU 可用、按量成本低。代价是模型冷启动、显存占用和运维；云端作为备选。

**Q4：视频为什么只抽帧 + ASR？**
> RAG 需要可检索的语义单元；30 秒关键帧 + 音轨转写能覆盖大部分讲解/演示场景。视频大模型成本高、时序定位难。需要动作/流程理解时再上视频模型或场景分割。

**Q5：长视频/大文件怎么处理？**
> 时长上限 1800 秒、上传上限 200MB；抽帧间隔可调；超限明确失败而不是拖垮服务。生产上会走异步队列、分片上传、资源隔离和超时。

**Q6：怎么保证重复导入不翻倍？**
> `file_title_id = md5(file_title)`；Milvus 先按 id 删除再插入；MinIO 图片前缀先清后传；媒体对象按日期/stem 覆盖。跨日期的旧目录需要清理策略。

**Q7：为什么不在 Milvus 加 modality/media_url 字段？**
> 加字段要重建 collection/迁移；当前把媒体 URL 放 content 前缀，零 schema 变更。代价是按模态过滤、统计不方便。后续可以 add field/双写/重建，按版本切换。

**Q8：多模态对 embedding 有影响吗？**
> 图片摘要、ASR 文本都会进入 chunk content；媒体 URL 前缀会增加少量 token，但不影响语义主体。我们给 chunk 300 字上限，URL 很短。需要控制时可以只在标题/首页 chunk 放 URL，或改成字段。

**Q9：怎么评估“多模态有没有用”？**
> 分桶：纯文本问题、图片问题、音频问题、视频问题；分别看 Recall@k、答案引用率、人工通过率。做消融：去掉图片摘要/ASR/关键帧，看指标下降。

**Q10：上生产还缺什么？**
> 异步任务队列、病毒扫描、ffmpeg 沙箱/资源限制、MinIO 私有读 + 签名 URL、多租户前缀、失败重试/死信、监控与成本告警、数据清理与版本化。

## 6. GraphRAG

### 6.1 业务问题

普通向量 RAG 擅长“语义相似”，但不擅长多跳和关系：
- “6-12 岁孩子晚睡会导致什么？”需要 `年龄段 → 晚睡 → 表现` 的路径；
- “这个方法适用于哪些问题？”需要实体关系；
- 用户希望答案能解释“依据哪条关系”，而不只是“某个 chunk 相似”。

### 6.2 架构与数据流

```text
导入：
chunks → NodeGraphExtraction（LLM 抽实体/关系）
       → 规范化（类型白名单/去空/去自环/去重）
       → Neo4j 单事务：删旧边 → MERGE 实体 → MERGE 关系 → 清理孤立节点

查询：
item_names → search_relations（按 item_name 锚定，degree 排序取 50）
           → 中文 bigram 交集精排 → top10
           → graph_chunks（id=rel_id）
           → 与向量/HyDE 一起进 RRF
```

### 6.3 3 分钟讲解稿

> “GraphRAG 我没有一上来做微软那种社区摘要，而是做了一个局部的实体关系检索。导入时在切片之后加一个抽取节点，让 LLM 按固定实体类型抽实体和关系：主题、年龄段、方法、问题、表现、建议、概念；关系用 2~6 字动词短语，description 限 200 字。抽完做规范化：空名丢弃、类型白名单、主体必须出现、端点缺失补全、自环丢弃、重复按 rel_id 去重。写入 Neo4j 用单事务：先按 file_title_id 删旧关系，再 MERGE 实体和关系，最后清理孤立实体，保证重复导入幂等。实体 id 用 `md5(item_name|name)`，按主体隔离，避免‘孩子’‘3 岁’跨主题合并成超级节点；关系 id 用 `md5(file_title_id|source|relation|target)`，同时作为 RRF 去重键。查询时按 item_names 过滤，degree 排序取 50 条候选，再用查询中文 bigram 和关系文本交集精排，取 top10；如果全零分就用 degree 兜底。图检索是增强路径，Neo4j 挂了就返回空，不影响主问答。图证据和向量/HyDE 一起进 RRF，id 稳定，量纲不同只看排名。这个方案不做全局主题摘要，因为当前问题是局部事实/多跳；需要‘整个知识库有哪些主题’时再上社区摘要和 Leiden。”

### 6.4 代码级细节

| 点 | 实现 |
|---|---|
| 实体 id | `md5(f"{item_name}|{name}")`，按主体隔离 |
| 关系 id | `md5(f"{file_title_id}|{source}|{relation}|{target}")`，稳定、可作 RRF 去重键 |
| 类型白名单 | 主题/年龄段/方法/问题/表现/建议/概念；未知归“概念” |
| 抽取批次 | 4000 字或 5 个 chunk；JSON 解析失败重试 1 次 |
| 写入 | 单事务：删旧边 → MERGE 实体 → MERGE 关系 → 清理孤立节点 |
| 约束/索引 | `Entity.entity_id` 唯一约束；item_name、file_title_id 索引 |
| 检索 | `item_name IN $item_names`；degree 排序取 50；bigram 交集取 top10 |
| 融合 | `graph_chunks` 作为 RRF 第三路；图权重初始 1，可调 0.8 |
| 降级 | 查询侧捕获 Neo4j 异常返回空；导入侧硬失败 |

### 6.5 关键取舍

| 问题 | 选择 | 为什么不选另一个 |
|---|---|---|
| 图的范围 | 局部实体关系子图 | 社区摘要/全局主题成本高、更新复杂；当前问题不需要 |
| 图数据库 | Neo4j 5 Community | Cypher/约束/事务/可视化成熟；替代 NebulaGraph 更适合超大规模 |
| 实体合并 | 按 item_name 隔离 | 避免跨主题超级节点；代价是同一实体跨主题不合并 |
| 图检索排序 | degree 兜底 + bigram 精排 | 比纯向量便宜；图规模大时可加图 embedding/路径打分 |
| 融合 | RRF | 图分数与向量分数不可比；只看排名稳定 |
| 抽取失败 | 导入硬失败 | 不能静默丢图；查询侧才软降级 |

### 6.6 难点与解决

1. **LLM 抽取不稳定**：固定 JSON、类型白名单、关系动词约束、端点补全、重试、规范化；抽样评估 P/R。
2. **重复/幂等**：rel_id 去重 + 单事务删旧边；重复导入关系数不增长。
3. **超级节点**：item_name 隔离 + 检索过滤 + degree 排序；后续可加实体对齐/同义词。
4. **图与向量融合**：RRF 只看排名；图证据 chunk 格式与向量对齐（id/title/content/source/score）。
5. **运维多一个组件**：Docker 部署、防火墙、备份、监控；小规模可先用单机。

### 6.7 怎么评估 GraphRAG

| 指标 | 方法 |
|---|---|
| 抽取质量 | 抽样 100~200 条关系，人工标 P/R/F1 |
| 多跳问答 | 构造需要 2~3 跳的问题，比较有图/无图的答案正确率 |
| 图检索命中 | 人工标相关关系，Recall@10 |
| 融合收益 | A/B：RRF 加图 vs 不加图；看答案通过率和引用率 |
| 延迟/成本 | 图查询 p95；抽取 token 成本/文档 |
| 图谱质量 | 实体数、关系数、度数分布、孤立节点比例 |

### 6.8 高频追问（10 问）

**Q1：什么场景需要 GraphRAG？**
> 多跳、关系、实体中心、需要解释路径的问题；简单事实题向量 RAG 足够。先做错误分析：如果错题里大量是“关系/多跳”，再上图。

**Q2：抽取质量怎么保证？**
> 提示词约束 + 类型白名单 + 端点补全 + 去重 + 抽样人工评估；JSON 失败重试；低质量时换模型/加 few-shot/规则后处理。不要假设 LLM 抽得全对。

**Q3：实体消歧怎么做？**
> 当前按 `item_name` 隔离，避免跨主题合并；同一主体内同名合并。跨主体同名不合并。后续可加同义词/实体链接/向量相似聚类。

**Q4：为什么不用 Milvus/Mongo 存图？**
> 多跳/路径查询用图数据库更自然；Milvus 是向量检索，不擅长关系遍历；Mongo 多跳查询复杂、性能差。代价是多一个运维组件。

**Q5：图检索为什么不用向量？**
> 图关系文本可以用 embedding，但当前规模用 bigram + degree 足够便宜；图规模大/语义复杂时可加关系 embedding 或路径打分。

**Q6：图与向量分数怎么融合？**
> RRF，只看排名；图分数不直接和余弦相似度比。图权重初始 1，效果不好再调 0.8/1.2；也可以按来源加权。

**Q7：抽取成本高吗？**
> 4000 字/5 chunk 一批，按文档规模线性；只对高价值文档抽；异步任务；模型可用小模型/批处理。成本要算进单文档导入成本。

**Q8：增量更新怎么做？**
> 按 file_title_id 删旧边再写；文档更新触发重新抽取；大规模用队列/版本号；失败可重试。

**Q9：为什么不做微软 GraphRAG 的社区摘要？**
> 当前是局部事实/多跳问题，社区摘要适合全局主题/大规模语料，构建和更新成本高。YAGNI；有全局问题再加 Leiden/社区摘要。

**Q10：上生产缺什么？**
> 图质量评估、增量/删除、权限与租户隔离、Neo4j 备份/监控/集群、Cypher 参数化、抽取成本控制、图谱版本化。

## 7. Agentic RAG

### 7.1 业务问题

固定“三路并行 → RRF → Rerank”的问题：
- 闲聊也走检索，浪费；
- 本地没有匹配时仍然查本地，查不到就结束；
- 一次检索不理想没有第二次机会；
- 复杂问题没有拆解。

目标：让系统自己决定“查哪里、查几次、够不够”，但保持有界、可观测、可回滚。

### 7.2 架构与数据流

```text
ItemNameConfirm
   ├─ 歧义反问 → AnswerOutput
   └─ QueryRouter
        ├─ direct → AnswerOutput
        ├─ web → WebSearch
        ├─ kb → [Embedding, HyDE]
        └─ both → [Embedding, HyDE, Web]
                       ↓
                      RRF → Rerank → RelevanceJudge
                                      ├─ 足够/达到上限 → AnswerOutput
                                      └─ 不足 → 清理旧结果 → 重写/升级 → 回到搜索
```

### 7.3 3 分钟讲解稿

> “Agentic 这块我刻意没有做成自由 ReAct Agent，而是用 LangGraph 状态机做离散决策，原因是线上问答需要 SSE 进度、成本上限和可解释性。第一个节点是路由器，输入原始问题、改写问题、已确认主体、历史、以及‘本地是否无匹配’，输出 kb/web/both/direct 和 1~3 个子问题；路由有白名单和兜底，本地无匹配时强制不允许 kb，避免无效检索。第二个节点是证据评估，放在 rerank 之后，拿 top5 切片判断是否足够；不足时输出 missing、重写问题和子问题，最多重试 2 次；如果本地 kb 不足，下一次自动升级到 web。重试前会清空上一轮的向量/HyDE/Web 结果，避免 RRF 复用脏数据。子问题会传进检索节点，普通检索、HyDE、Web 都支持多 query 并按 id/url 去重。所有 JSON 解析都有兜底：路由失败按有主体 both/无主体 web；评估失败按‘有结果即足够’，避免反而拖垮。最坏情况下额外约 13 次 LLM 调用，所以重试和子问题数都可配置。最终如果仍不足，答案提示词会要求明确说资料不足，不要编造。这套设计的核心是‘有界 Agentic’：有决策、有评估、有重试，但不会无限循环，也不会让模型自由调用任意工具。”

### 7.4 代码级细节

| 点 | 实现 |
|---|---|
| 路由 | `kb/web/both/direct`；白名单；`no_kb_match` 强制 web；JSON 失败兜底 |
| 主体确认改造 | 无匹配不再直接回“没有识别到”，返回 `no_kb_match=True` 交给路由 |
| 证据评估 | top5、每条 300 字；无结果直接不足；`enough` 兼容字符串；解析失败按足够 |
| 重试 | `loop_count` + `AGENTIC_MAX_RETRIES=2`；`loop_count > max` 退出 |
| 升级 | `route=kb` 且不足 → 下一次 `web` |
| 清理 | 不足时清空 `embedding_chunks/hyde_embedding_chunks/web_search_docs`，保留 `reranked_docs` 供最终回答 |
| 分解 | `sub_queries` 1~3；检索节点按 id/url 去重；HyDE 每个子问题一次 |
| 降级 | 单个 MCP 子问题失败跳过；全部失败返回空；Rerank 容错 |
| 循环上限 | LangGraph 默认 recursion_limit 25；重试调大时同步调高 |

### 7.5 关键取舍

| 问题 | 选择 | 为什么不选另一个 |
|---|---|---|
| 流程控制 | LangGraph 状态机 | 自由 Agent 丢 SSE 进度、成本不可控、难复现 |
| 路由位置 | 主体确认之后 | 复用 item_names/rewritten_query/history；代价是 direct 仍做一次主体识别 |
| 评估方式 | LLM judge + 无结果短路 | 纯阈值简单但不懂“是否足以回答”；LLM judge 有偏差，所以有兜底和上限 |
| 重试次数 | 2 | 边际收益递减、延迟/成本；0 太保守，3+ 不划算 |
| 失败处理 | 最终明说不足 | 不编造；比“硬答”更可信 |
| 本地无匹配 | 升级 web | 保留旧“没有识别到”会挡住网络回退；这是有意的行为变化 |

### 7.6 难点与解决

1. **路由误判**：白名单 + 规则强制（无主体不允许 kb）+ 兜底 + 黄金集评估 route accuracy。
2. **Judge 偏差**：严格 rubric、布尔解析、无结果短路、解析失败降级、人工抽检；judge 只决定是否重试，不决定事实。
3. **重试脏数据**：清空上一轮检索字段；只保留 `reranked_docs` 给最终答案。
4. **成本/延迟**：重试/子问题可配置；路由前置；可去掉 HyDE；小模型做路由/评估。
5. **死循环**：`loop_count` + 条件边；必要时提高 recursion_limit。
6. **MCP 超时**：每子问题 20 秒；单点失败跳过；全部失败交给评估。

### 7.7 怎么评估 Agentic 的收益

| 指标 | 方法 |
|---|---|
| 路由准确率 | 黄金集人工标 route，算混淆矩阵 |
| 重试率 | 日志 `loop_count` 分布 |
| 答案正确率 | 分桶：本地可答/本地不可答/闲聊 |
| 无答案拒答率 | 不可回答集，看是否敢说“不足” |
| p95 延迟 | 端到端埋点，分路由/重试次数 |
| 单次成本 | 路由/评估/HyDE/Web 的 token 与调用次数 |
| A/B | 固定 pipeline vs Agentic，控制问题和模型 |

### 7.8 高频追问（10 问）

**Q1：为什么不直接用 ReAct/OpenAI Agents 自由循环？**
> 在线问答需要可观测、可回滚、成本上限和 SSE 进度；自由 Agent 让模型决定调用哪些工具，难以保证这些。我的做法是把“决策”限制在四个路由和一次评估/重试上，流程仍由 LangGraph 管控。

**Q2：路由怎么保证不把该查本地的问题导到 web？**
> 提示词规则 + 白名单 + 兜底；`no_kb_match` 只允许 web/direct；用黄金集评估 route accuracy；上线先影子模式对比。

**Q3：LLM judge 可靠吗？**
> 不完全可靠，所以：无结果直接判不足、严格 rubric、布尔解析、解析失败按“有结果即足够”、最多 2 次、最终仍由 grounded prompt 约束。Judge 只决定是否重试，不直接生成事实。

**Q4：为什么最多 2 次重试？**
> 边际收益递减；每次重试增加 HyDE/评估/Web 调用和延迟；2 次足够覆盖“换查询/换通道”；再不够就明确说资料不足。

**Q5：查询分解会不会过度拆分？**
> 限制 1~3 个、要求独立完整、简单问题只给 1 个；检索结果按 id/url 去重；成本和效果都可评估。

**Q6：为什么不把路由放在主体确认之前？**
> 现在路由能复用 item_names/rewritten_query/history；代价是 direct 仍会做一次主体识别。更彻底的做法是路由前移，但会牵动历史保存和主体名回填，第一版不做。

**Q7：重试时怎么避免旧结果污染？**
> Judge 不足时清空三个检索字段；不清理 `reranked_docs`（最终回答还能引用已找到的资料）；下一轮搜索重新填充。

**Q8：Agentic 会不会更慢？**
> 会，多 1 次路由 + 最多 3 次评估 + HyDE/Web。所以重试和子问题可配置；路由先行避免无谓检索；可以只对复杂问题分解；路由/评估用小模型。

**Q9：怎么证明 Agentic 有用？**
> 黄金集分桶 + A/B：本地可答、本地不可答、闲聊；看正确率、拒答率、重试率、p95 延迟、单次成本。没有数据就不要说“提升 X%”。

**Q10：上生产还缺什么？**
> 异步任务/队列、分布式状态、限流/熔断、缓存、灰度/影子、prompt 版本化、路由/评估模型监控、成本告警、多租户隔离。

## 8. 引用溯源与文档跳转

### 8.1 业务问题

RAG 的答案如果没有来源，用户很难判断是“真回答”还是“模型编的”。产品需要：

- 答案里能看到“来自哪篇文档、第几页、第几段”；
- 点击引用能直接打开原文档对应位置；
- 引用必须可信，不能由模型随口生成页码和链接。

核心矛盾：**大模型很擅长写“第 5 页第 3 段”，但它并不知道页码。** 所以页码、段落、URL 必须来自入库元数据，模型只输出引用编号。

### 8.2 架构与数据流

```text
【导入】
原始文件 → MinIO（file_url，Content-Type 正确）
   ↓
NodePDFToMD → page_map.json
   （优先 MinerU content_list.json 的 page_idx，兜底 PyMuPDF 文本块）
   ↓
切分 → 主体识别（拿到 file_title_id）
   ↓
NodeCitationEnrich：每个 chunk 匹配页/块 → source_meta
   ↓
BGE-M3 → Milvus（source_meta 作为 JSON 字段一起入库）

【查询】
问题 → 检索（返回 source_meta）→ RRF → Rerank（保留元数据）
   ↓
AnswerOutput：context 变成「[1] 《文档》第5页第3段 + 内容」
   ↓
LLM 只输出 [1] → 后端把编号映射成 sources（页/段/URL）
   ↓
chat.html：行内 [1] 可点击 + 参考来源列表 → PDF #page=5
```

`source_meta` 的最小结构：

```json
{
  "doc_id": "md5(file_title)",
  "file_title": "万用表RS-12的使用",
  "file_url": "http://.../doc.pdf",
  "loc_type": "pdf",
  "page_no": 5,
  "paragraph_no": 3,
  "section": "## 直流电压档",
  "label": "《万用表RS-12的使用》第5页第3段",
  "anchor_text": "将旋钮转到直流电压档……"
}
```

### 8.3 3 分钟讲解稿

> “引用溯源这块我做的第一件事是明确边界：页码不能让模型生成。模型只做一件事——在支持某句话的句末输出 `[1]`，页码、段落、链接全部由后端从元数据映射。  
> 导入侧我在切分之后、向量化之前加了一个 `NodeCitationEnrich` 节点。PDF 的页映射优先用 MinerU 的 `content_list.json`，它每个 block 自带 `page_idx`；拿不到就用 PyMuPDF 按页提取文本块兜底。然后对每个 chunk 做中文 n-gram 匹配，定位到页码和页内 block 序号，写进 `source_meta`。  
> 存储上我只给 Milvus 加了一个 JSON 字段 `source_meta`，不拆成一堆列；检索节点把它带出来，Rerank 原来会把 chunk 重组成只剩 content/title/url/source，我改成保留元数据。  
> 答案生成时 context 是 `[1] 文档名 第5页第3段 + 内容`，提示词要求模型只引用编号。生成后后端解析 `[n]`，过滤非法编号，映射成 sources 数组，随 final 事件发给前端。前端把 `[n]` 渲染成可点击链接，PDF 用 `#page=5` 跳到对应页。  
> 页码准确率我抽 100 个 chunk 人工核对；链接能否打开还要依赖 MinIO 的 Content-Type 设置。段落高亮是二期，用 PDF.js 和 bbox 做。这个功能不难，难的是不让模型编、以及把页映射做准。”

### 8.4 代码级细节（面试官可能追问）

| 点 | 实现 |
|---|---|
| 页映射来源 | MinerU `content_list.json` 的 `page_idx` 优先；PyMuPDF `page.get_text("blocks")` 兜底 |
| 页号 | `page_idx + 1`，1 基 |
| 段号 | 页内 block 序号；不是 Word 自然段 |
| 匹配算法 | 中文 n-gram（默认 8）集合交集，取最高分页/块 |
| 写入节点 | `NodeCitationEnrich`，在 `NodeItemNameRecognition` 之后、BGE 之前 |
| 存储 | Milvus `source_meta` JSON 字段；旧版本可退化为 VARCHAR 存 JSON |
| 查询透传 | 检索 `output_fields` 加 `source_meta`；Rerank 保留 |
| 引用生成 | context 带 `[n]`；提示词要求只输出编号；后端正则解析 |
| 非法引用 | 超出 `sources` 范围的编号直接丢弃 |
| 兜底 | 模型没引用时展示前 3 个来源 |
| 跳转 | PDF `file_url#page=N`；音视频 `#t=秒`；Web 原 URL |
| 预览 | MinIO 上传必须设置 `Content-Type: application/pdf`，否则浏览器下载 |
| 安全 | 公开桶只适合演示；生产用私有桶 + 短时效签名 URL + ACL |

### 8.5 关键取舍

| 问题 | 选择 | 为什么不选另一个 |
|---|---|---|
| 页码怎么来 | 解析器元数据 + n-gram 匹配 | 让 LLM 生成页码一定会编 |
| 页映射来源 | MinerU content_list 优先 | PyMuPDF 对扫描件无文本层；content_list 有 OCR |
| 元数据存储 | Milvus 一个 JSON 字段 | 拆成 page/file_url/block 多列要改 schema 和查询；JSON 最小改动 |
| 引用方式 | 模型只出 `[n]`，后端映射 | 模型直接写链接/页码不可控、不可校验 |
| 跳转粒度 | MVP 页级 `#page=N` | 段落高亮要 PDF.js/bbox，工作量大；先验证引用价值 |
| 文档访问 | 演示公开 URL；生产签名 URL | 公开桶会泄露文档；签名 URL 有权限和时效 |
| 段落口径 | 解析器 block，不是自然段 | 自然段需要额外排版分析；block 足够定位 |

### 8.6 难点与解决

1. **页码不准**：优先 content_list；PyMuPDF 兜底；n-gram 调 6~10；抽样人工评估；匹配分太低时降级文档级。
2. **扫描件没有文本层**：PyMuPDF 提取不到文字，必须用 MinerU 的 OCR/content_list；两者都没有就只做文档级引用。
3. **跨页 chunk**：MVP 标起始页，`page_end` 等于 `page_no`；二期检测相邻页得分再做范围。
4. **模型不标引用/乱标**：提示词只允许给定编号；后端过滤非法编号；无引用时兜底展示前 3 个来源；用引用支持率评估。
5. **点击变下载**：MinIO 上传补 `Content-Type`；检查响应头；必要时走网关/PDF.js。
6. **权限**：公开桶不能用于真实文档；生产用私有桶 + 签名 URL + 检索前 ACL 过滤。

### 8.7 怎么评估引用

| 指标 | 方法 | 目标 |
|---|---|---|
| 页码准确率 | 抽 100 个 chunk 人工核对预测页 | 文本型 PDF >95% |
| 段号准确率 | 抽样核对 block 是否对应 | 先定义口径，再评估 |
| 引用合法率 | `[n]` 是否在 sources 范围内 | 接近 100% |
| 引用支持率 | 人工/LLM 判断引用是否支撑该句 | 抽样评估，持续优化 |
| 点击率 | 来源链接点击/会话数 | 判断引用是否有用 |
| 无引用率 | 答案没有 `[n]` 的比例 | 指导提示词优化 |

### 8.8 高频追问（10 问）

**Q1：怎么保证页码不是模型编的？**
> 模型只输出 `[n]`，页码和链接由后端从 `source_meta` 映射；模型根本拿不到“生成页码”的职责。非法编号会被过滤。

**Q2：页/段怎么定位？**
> 优先 MinerU `content_list.json` 的 `page_idx` + block 序号；没有就用 PyMuPDF 按页提取文本块。chunk 文本做中文 n-gram，匹配得分最高的页和块。

**Q3：为什么不让 LLM 直接输出“第 5 页第 3 段”？**
> 它会编，而且无法校验。页码是结构化元数据，应该由检索结果携带，不应该让生成模型猜。

**Q4：扫描 PDF 怎么办？**
> PyMuPDF 没有文本层，必须依赖 MinerU 的 OCR/content_list；两者都没有就降级为文档级引用，不硬标页码。

**Q5：跨页 chunk 怎么标？**
> MVP 标起始页，`page_end` 等于 `page_no`；二期用相邻页得分做范围。面试时说明这个边界。

**Q6：为什么在 Milvus 加 JSON 字段？迁移怎么办？**
> 一个字段承载所有定位信息，改动最小；拆成多列要改 schema、插入和查询。迁移可以新建 `kb_chunks_v2` 重导，或双写回填后切读路径。

**Q7：点击 PDF 为什么变成下载？**
> MinIO 上传没设 `Content-Type`，浏览器把 PDF 当二进制。上传时按后缀设置 `application/pdf`，或走网关/PDF.js。

**Q8：段落高亮怎么做？**
> 存 bbox 或 anchor_text，前端用 PDF.js 在文本层搜索/画高亮；这是二期，页级跳转先验证价值。

**Q9：引用准确率怎么评？**
> 抽 100 个 chunk 人工核对页码；引用支持率人工/LLM 抽检；统计非法引用率和无引用率；用点击率判断引用是否有用。

**Q10：安全和权限怎么处理？**
> 演示环境公开桶可以接受；生产必须私有桶 + 短时效签名 URL，检索前按租户/文档 ACL 过滤，不能靠 URL 保密。

## 9. 四者协同与技术演进

### 9.1 协同关系

```text
多模态：把图片/音频/视频变成文本 chunk
   ↓
GraphRAG：从文本 chunk 抽实体/关系，提供关系证据
   ↓
Agentic：决定查向量、查图、查 Web，还是直接回答
   ↓
引用溯源：chunk 带 source_meta，答案用 [n] 映射文档/页/段/链接
```

- 多模态让“内容”更全；
- GraphRAG 让“关系”可检索；
- Agentic 让“查哪里、查几次”自适应；
- 引用溯源让“答案依据”可核对、可跳转。
- 四者共享同一个 `item_name` 主体锚点和同一套 RRF/Rerank/答案链路。

### 9.2 演进阶段与何时加

| 阶段 | 能力 | 何时需要 | 成本 |
|---|---|---|---|
| RAG 1.0 | 向量 + 关键词混合 + RRF + Rerank | 起步 | 低 |
| RAG 2.0a 多模态 | 图片/音频/视频转文本 | 内容多模态 | 中（VL/ASR/ffmpeg） |
| RAG 2.0b GraphRAG | 实体关系子图 | 多跳/关系/可解释 | 中高（抽取 + Neo4j） |
| RAG 2.0c Agentic | 路由/评估/重试/分解 | Query 分布复杂、本地覆盖不足 | 中（额外 LLM） |
| RAG 2.0d 引用溯源 | 页/段定位、`[n]` 映射、文档跳转 | 用户需要核对答案、合规/审计 | 中（页映射 + 前端） |

> 面试时强调：**不是所有项目都要一次上齐**；先做错误分析，再决定加哪一层。这是技术判断力。

### 9.3 四者同时上线时的顺序

1. 先保证基础检索质量（切分、混合、RRF、Rerank）；
2. 多模态先扩内容，不改检索形态；
3. GraphRAG 作为增强路径，软降级；
4. Agentic 再改查询图，把图检索纳入路由；
5. 引用溯源最后接，先做页级跳转，再做段落高亮；
6. 每一步都有验收矩阵和回滚。

### 9.4 四个扩展的已知缺陷与改进优先级（面试加分项）

面试官问“这套方案有什么问题/如果重做”时，不要只说优点。主动列缺陷，说明你知道边界。

| 扩展 | 已知缺陷 | 改进方向 | 优先级 |
|---|---|---|---|
| 多模态 | VL 摘要可能丢细节；无视觉相似检索；ASR 有 WER；视频无场景检测；媒体信息占 chunk 文本 | 关键图 OCR/结构化抽取；CLIP 独立 collection；说话人分离/时间戳；场景切分替代固定抽帧；Milvus 加 modality 字段 | P2 |
| GraphRAG | LLM 抽取有噪声；实体消歧弱；大图更新/重建成本高；无全局主题摘要 | 抽取评估集 + few-shot/规则；实体链接/同义词；按文档增量更新；Leiden 社区摘要 | P1（质量）/P3（全局） |
| Agentic | 路由/评估可能误判；额外延迟和成本；状态在多实例下需外置；judge 有偏差 | 黄金集校准 route/judge；小模型；缓存；Redis 状态；人工抽检 | P1（评估）/P2（性能） |
| 引用溯源 | 页映射可能不准；扫描件无文本层；跨页只标起始页；段落高亮未做；公开 URL 有权限风险 | content_list 优先；抽样评估；二期 bbox/PDF.js 高亮；私有桶 + 签名 URL | P1（准确率）/P2（高亮/权限） |
| 基础工程 | 任务队列在内存、单进程；无多租户/权限；无生产监控 | Redis/队列、分布式 trace、tenant/ACL、告警 | P0（上生产前） |

**改进优先级建议：**

1. 先补评估与可观测（没有指标，后面都是盲调）；
2. 再补异步任务/队列、多租户/权限、监控告警；
3. 然后按错误分析决定是多模态、图还是 Agentic 继续投入；
4. 视觉相似检索、全局图摘要属于明确需求出现后再做。

### 9.5 验收要点速览

| 扩展 | 最小验收集 |
|---|---|
| 多模态 | 5 类文件路由；图片/音频/视频完整导入；ASR 非空；关键帧生成；重复导入不翻倍；静音/超长/超大明确失败；答案回传媒体 URL |
| GraphRAG | 约束/索引存在；写图成功；重复导入关系不增长；按 item_name 查出关系；RRF 含图 id；Neo4j 停机查询降级、导入失败 |
| Agentic | 四类路由；无主体不允许 kb；空结果 judge 判不足；kb→web 升级；重试 ≤2；MCP 失败不崩溃；最终不足提示不编造；原问题回归通过 |
| 引用溯源 | 页映射生成；chunk 有 source_meta；Milvus 可查；答案有 `[n]` 和 sources；PDF 跳页；非法编号过滤；无引用兜底；Markdown/扫描件降级合理 |

## 10. 系统设计题（50k 级）

### 10.1 设计一个多租户企业知识库 RAG

**回答框架：目标 → 数据模型 → 检索 → 权限 → 运维 → 取舍。**

- 数据模型：所有数据带 `tenant_id`；Milvus 用 partition key/标量过滤；Neo4j 实体/关系带 tenant；MinIO 按租户前缀；Mongo 按租户+session。
- 检索：每次 query 强制带 tenant 过滤；不能在 prompt 里做权限；图检索、Web、缓存都要带租户。
- 权限：文档 ACL（用户/部门/角色）；检索前过滤，检索后再校验引用；审计日志。
- 隔离 vs 成本：共享 collection + tenant 过滤 vs 每租户独立 collection；大客户独立，小客户共享。
- 运维：配额、限流、成本分摊、数据删除、备份。
- 验证：跨租户泄露测试、权限矩阵测试、压测。

### 10.2 如何建立 RAG 评估体系

**四层：**

1. **检索层**：黄金集（问题 + 相关 chunk 标注）；Recall@k、MRR、nDCG；分桶（文本/图片/音频/视频/多跳）。
2. **生成层**：正确性、忠实度（groundedness）、引用准确性、完整性、拒答；人工 rubric + LLM judge 校准。
3. **系统层**：p50/p95 延迟、成功率、单次成本、导入成功率、重试率、路由准确率。
4. **线上层**：用户反馈、点赞/点踩、追问率、转人工率、会话完成率；A/B。

**关键**：黄金集要覆盖可回答/不可回答/对抗问题；LLM judge 要人工抽检校准；每次 prompt/模型/索引变更跑回归。

### 10.3 如何降低幻觉

- 检索质量：混合检索、rerank、动态 top-k、主体过滤；
- 生成约束：只基于参考内容、引用来源、资料不足要拒答；
- 验证：答案与引用一致性检查、关键事实二次核对；
- 工程：temperature 低、结构化输出、失败重试；
- 评估：不可回答集、groundedness、人工抽检；
- 不要用“让模型更自信”的提示词。

### 10.4 增量更新与删除

- 文档版本号 + `file_title_id`；
- 导入幂等：先删后插（Milvus/Neo4j）；
- 软删除/墓碑，异步重建索引；
- 缓存失效：query cache、embedding cache、rerank cache；
- 图：按 file_title_id 删边、清理孤立节点；
- 对象存储：按日期/版本清理旧媒体；
- 验证：更新后旧内容不再被检索到。

### 10.5 高并发与低延迟

- 异步任务队列（导入与查询分离）；
- embedding/rerank 批处理；
- 缓存：query→结果、embedding、rerank、图查询；
- Milvus：HNSW/IVF 调参、副本、分区；
- Neo4j：索引、限制候选、超时；
- 流式输出首 token；
- 超时/熔断/降级：Web 失败返回空、图失败返回空；
- 压测与容量规划。

### 10.6 权限与数据安全

- 上传：后缀白名单、大小上限、basename、病毒扫描、ffmpeg 沙箱；
- 检索：tenant/ACL 过滤，不能只靠 prompt；
- 存储：MinIO 私有桶 + 签名 URL；加密；
- 模型：数据不出内网/脱敏；日志脱敏；
- 提示词注入：检索内容当数据、不执行其中指令；输出过滤；
- 审计：谁在何时查了什么。

### 10.7 可观测性

- 每个节点：耗时、输入/输出 token、检索条数、命中来源；
- 每次 query：route、sub_queries、retry、evidence、最终答案；
- 指标：成功率、p95、成本、重试率、拒答率、无结果率；
- 告警：错误率、延迟、MCP/Neo4j/Milvus 健康；
- Trace：OpenTelemetry/请求 ID 贯穿导入与查询。

### 10.8 成本控制

- 路由/评估用小模型；
- 只对复杂问题分解；
- HyDE 可关；
- Rerank 只对 top N；
- 缓存高频 query/embedding；
- 图抽取只对高价值文档；
- 媒体转码/ASR 异步、限流；
- 按租户配额与成本分摊。

### 10.9 选型对比

| 场景 | 选择 | 说明 |
|---|---|---|
| 向量库 | Milvus | 原生稠密+稀疏混合；规模大；运维重 |
| 小规模 | pgvector | 与业务库同源，简单；混合检索弱 |
| 关键词 | Elasticsearch | BM25 强；与向量融合需额外工作 |
| 图 | Neo4j | Cypher/事务/可视化；超大规模看 NebulaGraph |
| 对象存储 | MinIO | S3 兼容、自托管；生产可换云 OSS |
| 会话 | MongoDB | 灵活；强一致/事务要求高可换 PostgreSQL |

### 10.10 容量与成本估算（面试可讲）

不要背数字，记住公式，现场按面试官给的规模算。

**向量存储**

```text
原始向量 ≈ chunk 数 × 维度 × 4 字节（float32）
索引/副本开销 ≈ 原始向量 × 1.5 ~ 2
```

例：100 万 chunk × 1024 维 × 4 字节 ≈ 4.1 GB 原始稠密向量；加索引/副本约 8~12 GB。稀疏向量按实际非零项另算。

**Embedding 吞吐**

```text
总耗时 ≈ chunk 数 / (batch_size × 每秒批次数)
```

代码里按 3 条一批是为显存保守；生产可压测后调大 batch。

**图谱规模**

```text
关系数 ≈ 文档数 × 每文档关系数（抽取上限 40）
存储 ≈ 节点/关系数 × 单条属性大小 + 索引
```

例：1 万文档 × 30 条关系 = 30 万条边，Neo4j 单机可承载；关键是索引和检索候选上限。

**单次查询成本**

```text
cost ≈ Σ(prompt_tokens + completion_tokens) × 模型单价
     + embedding/rerank 调用
     + 向量/图/对象存储
```

Agentic 最坏约 13 次额外 LLM 调用（路由 1 + 评估 3 + HyDE 9），实际大多数首轮结束。用日志统计 P50/P95 调用次数，别用最坏值吓自己。

**媒体存储**

```text
MinIO ≈ 原文件大小 + 关键帧（帧数 × 单帧大小）+ 图片副本
```

按 30 秒一帧、单帧 100~300KB 估算；长视频要设时长/帧数上限。

### 10.11 如何设计引用溯源与文档跳转

**回答框架：元数据 → 存储 → 查询透传 → 答案映射 → 跳转/权限。**

- 元数据：chunk 入库时带 `source_meta`（doc_id、file_url、loc_type、page_no、paragraph_no、label）；PDF 优先用 MinerU `content_list.json` 的 `page_idx`，兜底 PyMuPDF。
- 存储：Milvus 加一个 JSON 字段；不要拆多列，除非要按页过滤。
- 查询：检索 `output_fields` 带出元数据，Rerank 保留；不要让模型生成页码。
- 答案：context 带 `[n]`，模型只输出编号；后端映射 `sources`，非法编号过滤。
- 跳转：PDF `#page=N`；音视频 `#t=秒`；Markdown 用章节锚点；Web 原 URL。
- 权限：引用链接也要走 ACL；生产用私有桶 + 短时效签名 URL，不能靠 URL 保密。
- 评估：页码准确率、引用支持率、非法引用率、点击率。

## 12. 行为面 STAR

### 故事 1：LLM 抽取/路由 JSON 不稳定

- **S**：GraphRAG 抽取和 Agentic 路由都依赖 LLM 输出 JSON，模型偶尔加解释、代码块或字段类型不对。
- **T**：不能因为一次解析失败就让导入/查询失败。
- **A**：提示词限定“只输出 JSON”；解析时去代码块、截取首尾大括号；字段做类型兼容（`enough` 字符串转布尔）；失败重试/兜底；抽取结果做规范化和白名单。
- **R**：链路不会因单次格式问题崩溃；坏数据被丢弃或降级，而不是写进库。可进一步加 few-shot/结构化输出。

### 故事 2：MCP 搜索故障拖垮整个问答

- **S**：原 Web 搜索节点没有异常处理，MCP 超时/报错会让整个查询 500。
- **T**：Web 是增强路径，不应该影响本地问答。
- **A**：按子问题 try/except，失败跳过；全部失败返回空；评估节点判定不足；最终答案提示资料不足。加 20 秒超时。
- **R**：MCP 故障时查询仍可用，只是答案质量下降；符合“增强路径软失败、核心路径硬失败”的原则。

### 故事 3：多模态方案取舍（不做 CLIP）

- **S**：图片/音频/视频要进知识库，最直接的想法是每种模态建一套向量。
- **T**：在有限时间内让多模态内容可检索，且不破坏现有链路。
- **A**：对比“多模态向量”vs“统一转 Markdown”：后者复用切分/向量/检索/重排，成本低、可解释；先不做 CLIP，把“以图搜图”列为后置需求；用 VL 摘要 + 上下文保留关键信息。
- **R**：新增 4 类文件支持，检索链路零改动；明确记录取舍和后续升级路径。

### 故事 4：为什么要做有界 Agentic，而不是自由 Agent

- **S**：固定三路并行无法覆盖“本地没有/需要多跳/需要多查一次”的问题。
- **T**：提升覆盖率，同时保证 SSE 进度、成本和可回滚。
- **A**：把决策限制为 4 个路由 + 证据评估 + 最多 2 次重试；本地不足升级 web；所有 JSON 有兜底；重试清空旧结果；不引入自由工具调用。
- **R**：系统具备自适应能力，但流程仍是可观测状态机；最坏成本可估算（约 13 次额外 LLM 调用）。

### 故事 5：工程化与验收

- **S**：四个扩展都涉及多存储、多外部服务，容易“跑通一次”但不可重复。
- **T**：保证重复导入、失败、回滚都可控。
- **A**：每阶段写验收矩阵（V1~V15）；幂等 id；单事务写图；上传校验；降级策略；回滚步骤；节点级进度。
- **R**：方案可交付、可验证；面试时能说清“怎么证明它对”。

### 故事 6：引用页码不准怎么定位

- **S**：上线引用后，用户反馈“点进去不是那一页”，日志里没有页映射来源。
- **T**：在不改检索链路的前提下，快速定位是解析器、匹配算法还是前端链接的问题。
- **A**：把 `page_map.json` 的 `source`（MinerU/PyMuPDF）和匹配分数记进日志；抽样 100 个 chunk 人工核对；发现扫描件走 PyMuPDF 没有文本层，改为优先 content_list；短 chunk 匹配不稳，调 n-gram 长度；前端链接统一从 `source_meta.page_no` 生成。
- **R**：页码准确率可量化、可回归；扫描件和跨页有明确降级边界，不再靠猜。

## 14. 白板速写

### 14.1 RRF

```python
def rrf(rank_lists, k=60, top_n=10):
    scores = {}
    chunk_map = {}
    for chunks in rank_lists:
        for rank, chunk in enumerate(chunks, start=1):
            cid = chunk["id"]
            scores[cid] = scores.get(cid, 0.0) + 1.0 / (k + rank)
            chunk_map.setdefault(cid, chunk)
    ordered = sorted(scores.items(), key=lambda item: item[1], reverse=True)
    return [
        {**chunk_map[cid], "score": score}
        for cid, score in ordered[:top_n]
    ]
```

def locate_page(chunk_text, page_grams, n=8):
    chunk_grams = build_grams(chunk_text, n)
    best_page, best_score = None, 0

## 15. 面试前 10 分钟速查

### 15.1 必须记住的数字

| 数字 | 含义 |
|---|---|
| 300 / 50 | chunk_size / overlap |

| 18 | Rerank 最大候选 |
| 30 RPM | VL 图片摘要限流 |
| 30 秒 | 视频抽帧间隔（默认） |
| 200MB / 1800s | 上传上限 / 视频时长上限 |
| 2 | Agentic 最大重试次数 |
| 3 | 单次最大子问题数 |
| 13 | Agentic 最坏额外 LLM 调用估算 |
| 4000 字 / 5 chunk | 图谱抽取批次 |
| 50 / 10 | 图检索候选 / 返回 |

### 15.2 四个取舍（必须能展开）

1. **统一 Markdown vs 多模态向量**：复用链路/成本/可解释 vs 视觉相似能力；何时加 CLIP。
2. **局部 GraphRAG vs 微软社区摘要**：局部关系/成本/更新 vs 全局主题；何时加 Leiden。
3. **有界 Agentic vs 自由 Agent**：SSE/成本/可复现/安全 vs 开放式工具调用；何时另建 Agent 服务。
4. **模型生成页码 vs 元数据映射**：元数据可校验、不编造 vs 页映射开发成本；何时做段落高亮。

### 15.3 四个失败模式（必须能讲）

1. **LLM JSON 不稳定**：提示词 + 解析 + 重试 + 兜底 + 规范化。
2. **MCP/Neo4j 故障**：增强路径软降级，核心路径硬失败。
3. **重试脏数据/死循环**：清空旧检索结果 + `loop_count` + 上限 + recursion_limit。
4. **页映射失败/引用伪造**：降级文档级；模型只出 `[n]`，非法编号过滤。

### 15.4 四个指标（必须能定义）

1. **Recall@k**：黄金集相关切片是否进 top-k。
2. **Groundedness/答案通过率**：答案是否有引用支撑、人工 rubric 是否通过。
3. **p95 延迟 / 单次成本**：端到端埋点 + token/调用次数。
4. **页码准确率 / 引用支持率**：抽样核对页号；引用是否真的支撑该句。
